# 角色、范围、授权与职责分离
八个基础角色保持稳定；“体验会员/已认证/受限制”是成员状态，不额外复制一套角色。成长等级也不是权限角色。

| 角色 | 可做 | 明确不能做 | 默认范围 |
|---|---|---|---|
| STUDENT | 报名、提交、兑换、本人明细/申诉 | 查看他人档案、改分、审批 | 本人 |
| STUDENT_ORGANIZER | 提议活动、受托组织、事实签认、团队材料 | 自发自审、改规则、终审团队高分 | 指派活动/项目 |
| MENTOR | 技术验收、考核、建议分配 | 自审本人受益、直接改余额 | 指派课程/项目 |
| REVIEWER | 身份/积分/竞赛/违规审核、独立复核 | 跳过回避/双审、删历史 | 指定组织及职责 |
| OPS_MANAGER | 奖品、活动、预算草案、采购入库申请 | 单独批准本人调整、替代教员重大决定 | 组织运营 |
| REWARD_OPERATOR | 备货、核对、扫码、盘点提报 | 手改库存、查完整学生档案、补分 | 指定领取点 |
| AUDITOR | 读必要账本/日志、抽样、风险标记、复核报告 | 决策本人审计对象、直接记账 | 分配审计范围 |
| SYSTEM_ADMIN | 技术配置、健康、备份、账号恢复流程 | 默认全量私人数据、业务改分、给自己业务角色 | 技术边界 |

## 真实授权不同于角色Seed
角色定义是版本化代码；某个真人拥有某角色是数据库记录（开始/结束时间、范围、授权申请/批准人、依据）。不得按姓名或前端localStorage判断管理员。
授权/撤销本身写审计。首次安装通过本机一次性bootstrap建立技术管理员；业务REVIEWER由真实负责人确认，禁止默认密码。生产需两个不同自然人满足双审；不存在真实人员时不能以两个测试账号冒充双审。
Demo可用22个虚构用户（15学生+7职员），其账号均标demoOnly，永不迁入生产。

## 核心权限代码（详见permissions.json）
`profile.read.self`、`activity.register`、`attendance.confirm.assigned`、`submission.create.self`、`project.review.assigned`、`approval.decide`、`reward.manage`、`inventory.adjust.request`、`pickup.fulfill.site`、`audit.read.scoped`、`appeal.review.independent`、`system.configure`。
对每个请求，检查permission+organizationId+resource ownership/assignment+siteId+状态前置条件。前端隐藏按钮只改善体验，不构成鉴权。

## 多重角色与回避
同一账户两个角色不能在同一审批步骤算两个人。委派、代领、自审、同团队直接受益均保存关系快照；组织者可以证明到场，但不能独自完成自己积分的终审。低风险自动入账需要预批准规则和可信证据，不能靠上传“签到成功”截图触发。
仓管拿到扫码结果只能看必要核验信息、订单规格、本站点状态，不查看学号全值、处罚历史或成长档案。

## 导入与导出
真实学生名单不进入Git；后台上传→预览→校验→批次提交→导出错误行→审计。CSV出站防公式注入，所有导出有scope过滤、记录导出者和用途，下载令牌短期有效。批量授权必须预览范围与逐条返回，避免“全表成功”掩盖部分失败。
