# 粤木木系统：自主产品升级与对抗式审查

你现在位于已经完成主要功能开发的“粤木木无人机积分奖励系统”原项目中。本轮由当前这一个任务窗口端到端负责。请实际研究、设计、开发、运行、检查和修正，不要只交建议、概念图或计划。

## 1. 任务目标：你负责做产品判断，而不是照着旧版清单装修

学生端小程序与教员管理端已经具备主要业务功能，但我不满意目前的视觉完成度、品牌辨识度和部分操作体验。旧版优化提示词对颜色、首页模块、菜单数量和实现方式规定过多。本轮这些设计规定不再是验收标准；保留经过核实的业务事实与安全边界，由你重新判断什么设计真正适合这个系统。

请把它当成一次有充分创作空间的产品升级，而不是在 V3 上再换一次皮肤。重点是学生端，同时全面检查教员端、内容、流程衔接和工程质量中值得改善的地方。不要把“目前功能大体能用”理解成“现有交互不能质疑”，也不要把“大胆改”理解成必须全部重写。

学生第一次打开时，应理解这里能帮助自己参与哪些真实的无人机训练、学习、装调实践、项目和俱乐部活动，并产生参与的兴趣；老用户应能快速继续自己的事情。积分、成长、翼章和奖励应支持这种体验，而不是把整个产品压成一个积分钱包。教员应能少寻找、少记忆、少重复输入，直接处理当前角色真正需要处理的事务。

请自行识别问题、排序、选择方向并实现。日常设计和工程取舍不需要逐项问我。

## 2. 你的自主权，以及少数不可擅自改变的底线

你可以重新设计配色、字体层级、布局、导航、页面组合、插画、摄影语言、图标、动效、内容表达和交互方式；可以重构前端组件，调整路由和信息架构，补充确有价值的体验能力及其必要的接口支持。原来的五个学生标签、六个后台工作域、蓝白黄配色、首页卡片顺序、三个样板页都不是必须遵守的答案。深色、浅色、编辑式版面、插画、场景渲染或其他方向，均可根据实际效果选择，不必迎合某种固定模板。

可以合并重复入口、删除无用装饰、减少无意义的操作，甚至推翻不合适的页面结构。保留业务能力不等于保留每张旧页面；通过迁移或跳转保证重要旧入口可找到对应的新功能。

只守住以下底线：

- 保护现有工作与数据。先检查仓库状态、项目约定和运行环境，采取可回退的改动方式；不覆盖用户未提交修改，不破坏性重置、不清库，不在真实业务数据上制造测试交易。
- 不擅自改变实质业务权益与权限。木能量、成长里程、技能翼章的含义，余额与库存处理、审批独立性、回避、核销确认、审计和个人数据权限，以真实项目规则为准。必要的业务制度修改单独提出，得到确认后实施；不要用跳过审核换取更少点击。
- 保持真实性。不能虚构开放的课程、资质、商品、名额、积分、评价、成功状态和测试结论，不冒用他人素材或标识。新付费服务、公开部署、向外部发送私密数据等实质新增授权事项先确认。美化、截图和测试使用独立演示环境，演示内容自然可信并明确标识，不改写真实记录掩盖问题。

除此之外，设计手段和实现细节由你负责。

## 3. 先理解真实系统，再借鉴优秀案例；不要研究完仍然只会拼卡片

读取当前仓库的说明、项目约定、实际页面、数据、接口、权限和已有资源，启动能够运行的两端，记录关键任务及当前截图。历史提示词和指导书是线索，不是当前实现的唯一事实来源。若项目里只有说明文件，先确认正确源码位置，不要把静态指导书当作可运行系统。

如存在随本任务提供的《02_案例研究与V3观察.md》，把它作为研究起点，不要机械照搬其中的迁移建议。它只检查了上传包里的首页截图和指南，没有实测你的整个系统。

主动浏览优秀小程序及其官方获奖记录、设计团队复盘、界面图片和能够取得的流程材料。可从云游敦煌、佳士得 Live Auction 微信小程序、云游长城、东芝家电小程序、StoryTeller、青松助手、西门子官方小程序入手，并补充与你发现的问题更相关的案例。

研究的是：品牌如何进入界面细节，内容如何组织，用户如何找到下一步，复杂服务如何连起来，新用户如何开始，重复使用如何省力。区分真实小程序、原生 App、网页和纯概念稿；奖项、实际用户数据和设计师主张分开记录。没有访问或验证的交互，不要写成亲测。

不要套用某一家产品的整套版式，也不要把无人机照片放进通用后台卡片就叫品牌升级。先形成少量真正不同的可视方向，用同一批真实业务内容比较效果，自行选择并说明关键取舍，不要停下来等我选颜色。研究与探索做到足够支撑选择就进入实现，不要用长篇分析替代开发。

## 4. 用结果判断设计，不预先限定页面长什么样

学生端需要兼顾吸引参与和完成任务。请自己重新决定首屏应该展示什么、哪些信息应后移，以及首次访问和重复使用是否应有所区别。训练、学习、装调、团队项目、俱乐部与奖励的关系，需要通过真实内容与交互变得清楚，而不是堆关键词。

关注整个体验，不仅是首页：用户如何理解活动、判断是否能参加、完成报名与成果提交、理解审核进度、找到自己的项目、看懂成长、兑换并领取奖励。页面重排后，这些事情应更清楚，而不是因为入口藏起来而表面更简洁。

教员端不要以“菜单数量更少”作为成功证据。围绕实际任务审视信息能否在需要时出现、材料是否要跨页面拼凑、操作结果是否确定、不同角色是否被无关功能打扰。可以改变工作台、导航和详情交互，但分类、聚合或搜索只是手段，不是预定答案。

图片、动效、排版与文案由你一起负责。主动检查当前环境真正可用的生成、编辑、渲染和浏览器工具，完成素材制作、目检、裁切、压缩、接入和页面复查，而不是把素材任务留给另一个窗口。生图能力受限时优先寻找项目内授权资源或合适的原创替代，并如实说明缺口，不以一堆占位图宣称完成。

无人机视觉须符合所表现的机型；展示四旋翼 FPV 时检查电机、旋翼、机臂及器材结构，不能靠提示词写了“四旋翼”就默认正确。使用已有真实品牌标识，不重画成近似校徽，不把技能翼章伪装成正式执照。商品图片应与实际奖励相符。

动效可以有创意，但应帮助理解、反馈或建立情绪，而不是增加等待。文字和操作应是真实可访问的界面，不把整页生成为一张不可交互的大图。在目标小程序运行时中处理触控、键盘、安全区、字体、资源体积、慢网和减少非必要动画的需求，不用网页效果冒充真机适配。

## 5. 对抗式审查：刻意寻找自己方案最可能失败的地方

在当前窗口中依次切换审查视角，不需要我再开其他窗口。它们是结构化的自我检查，不是独立专家投票或真实用户调研。初稿实现后，先尝试反驳自己的方案，再决定修什么。

挑剔的设计评审：去掉 Logo 和名字，这个界面是否仍有无人机俱乐部的辨识度？图片、字体、组件、文案和动效是否像同一个产品？所谓高级感是否只来自一张漂亮封面？二级页面是否马上退回普通表单模板？

第一次使用的学生：零积分、零翼章、没有参加过活动时，他能否理解能做什么、第一步是什么？陌生术语是否造成门槛？看起来很热闹的服务是否真的能用？

经常使用的学生：下一场训练、待补材料、待领取奖励和许多未读通知同时出现时，哪些信息真正重要？返回页面是否保持合理状态？他是否每次都得重新寻找同一件事？

不熟悉系统的教员：拿到一条真实待办后，能否看懂对象、证据、前序处理、当前权限和下一步？是否还需要记编号、换菜单、查另一张表？拒绝、补材料、无权处理或需要独立复核时是否清楚？

移动端与失败场景：长标题、大字、空数据、很多条记录、小屏、键盘弹起、慢网、图片或上传失败、登录过期会怎样？提交后网络中断时，用户能否确认实际状态？连续点击会不会产生重复业务？不要把未知结果直接表现成成功或失败。

业务与隐私审查：新导航是否只在前端隐藏权限？不同用户会不会串看资料？积分、库存、审批与核销是否仍遵守原规则？截图和日志是否暴露敏感信息？漂亮界面是否掩盖真实限制或增加误操作？

把重要发现写成“具体场景与截图/操作证据 → 问题与影响 → 修正或保留理由 → 复测结果”。至少完成一轮实现后的专项反驳与复测，针对高影响问题继续迭代；没有证据就标为待验证，不为凑数编问题，不给自己打一个高分就结束。

这些是起点。你应继续发现我没有想到的问题，尤其注意审美、学习成本、内容质量、效率、反馈、性能和制度安全之间的冲突。保留仍然存在的取舍，不假装所有目标都能同时做到最好。

## 6. 交付的是可用产品，以及足以判断改善的证据

在实际项目里完成改动并运行，分阶段检查，覆盖受影响的主要页面和业务链路。先让所选方向在真实页面上成立，再推广；具体实施顺序由你决定。按当前工程能力做测试，需要新的轻量测试时自行补充，不把“旧版测试通过”当作新版验收。

用改前改后的实际运行截图和相同任务对比说明变化。对重要链路记录必要跳转、输入、状态理解或其他有意义的指标，同时记录测试条件。模型走查、浏览器自动化、微信开发者工具和真机检查分别说明；没有真实用户测试，不声称满意度或效率提升百分比。

最终给我：实际完成的学生端与后台升级、关键设计取舍、重要流程变化与功能去向、实际使用的素材与动效、对抗审查导致的修正、测试证据、尚未验证或未解决的事项，以及当前如何运行。

保持少量、持续更新的任务记录即可，不必创建大量重复文档。任务较长时保存决定、进度和剩余工作，不用回顾旧分析代替推进；遇到确实需要我提供的权限或业务决策时说明具体阻塞，并继续不受影响的工作。

现在开始检查原项目。你不需要执行我过去规定的页面模板，也不需要另一个窗口配合。请对最终产品的辨识度、可用性和完成度负责，用实际结果证明这次升级值得做。
